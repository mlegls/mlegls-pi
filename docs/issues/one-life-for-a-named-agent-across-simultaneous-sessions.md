idea: "I think we should change my optmem to have named profiles, rather than being per session. originally i intended to just keep optmem sessions around for a long time, but i think this would be a better ux. and then each concept agent could be an optmem profile. i don't see much point to using this kind of logarithmic memory system for a short session." Then, having worked out what kind of creature the mechanics imply: "If what we want is one 'creature' with the capacity for simultaneous manifestations, because simultaneous manifestations is advantageous in many ways over not being able to manifest simultaneously, so we see this as a 'capability' of the creature", and "let's start on revising my pi optmem to a realization of this, then. It seems to deserve a rename though. Maybe 'hydra'?" (maintainer, 2026-11-11, Hermes concept-strategy desktop session `20261111_184900_7d1d9e`).

goal: [optmem](../../extensions/context/life/index.ts)'s successor is a named life that any number of sessions are attached to at once. A life is one agent's chat that never ends (the word is the Connectome port's, `extensions/connectome/README.md` at `b40cdecd^`); a manifestation is a session attached to it. Optmem has only a past. A creature that can be in several places also needs a present: where it is now and what each of it holds.

The situation it's for: mlegls is in a bb thread with Concept Engineering about one issue while a second thread of it shapes another and a scheduled run of it fires. Each knows the others are running and what they hold. What one finished, the others remember from their next run on, marked with where it happened. A message to Concept Engineering reaches it while it is busy. Today each of those is a gap in Hermes, where the four Concept agents live: a busy bot can't be messaged, a second session on a profile shares none of the first's history, and two writers on one profile's memory are warned against.

It runs beside [notes](../../extensions/context/notes.ts), which stays as it is: "the mechanic is a way to track 'experiential' history with the capacity for simultaneous manifestation. And you could use life and notes at the same time." The life is what one agent lived; notes are what any agent in the project wrote down.

Out: the agent's soul and agent-scoped skills ("agent-scoped skills could also be implemented as a pi extension or bb plugin"), which are files and separable.

## shape

Proposed by concept-strategy in the session above, accepted by the maintainer as the basis (decisions), and checked against the code in @thread:thr_zig6b69pjn, which changed four things: the log holds copies, not references; positions come from SQLite's write lock; builders take leases; and a long run appends before its boundary can move. Each is marked below.

`extensions/context/optmem/` becomes `extensions/context/life/` (`git mv`, then edit): `tree.ts`, `cache.ts` and `score.ts` move unchanged, with their tests; `log.ts`, `build.ts`, `index.ts` and the prompt change as below; `present.ts` is new. Schema names, settings (`memory.schemas.life`, same fields as optmem's) and the mechanism name become `life`; mentions of optmem in [index.ts](../../extensions/context/index.ts), [mechanism.ts](../../extensions/context/mechanism.ts), [elide.ts](../../extensions/context/elide.ts) and the [notes](../../extensions/context/notes.ts) header follow. Existing `optmem` records stay in the store unread.

- **names and attaching.** A life's id is `<git common dir>:<name>` (project-scoped, as notes' `projectOf` keys the project log) or `/<name>` for machine-wide, as the Connectome port did. The Concept agents work across repositories (this was filed from one working here), so theirs are machine-wide. `/life <name>` attaches the session and `/life off` detaches; the choice is a session entry, so resume and forks keep it. `PI_LIFE=<name>` attaches at start, and the extension deletes it from `process.env` once read, so nothing the manifestation launches inherits it. The mechanism is on exactly when the session is attached; otherwise OM (the default) is. A life is attached to its name alone: changing model keeps the life. Attaching a session that already has history appends its unappended branch as one run.
- **log.** A life's messages are records of schema `life` in the [records store](../../lib/records/store.ts), one per optmem message (`messagesOf` in [log.ts](../../extensions/context/life/log.ts): an entry yields several), body the message's text, tags `life.id`, `life.pos`, `life.kind`, `life.place`, `life.date` (the entry's own timestamp), `life.model` (provider/id: an assistant message's own, otherwise the session's at that point) and `life.source` (`entry:<session>/<entry>#<k>`, [branch.ts](../../lib/records/branch.ts)'s ref plus the position in the entry). *Changed from the proposal, which had references to session entries:* pi session files belong to bb threads that can be deleted, the life would have to read every manifestation's file to build itself, and a copy is indexed by the store's full-text index, so `recall` searches the life with no change. The ref keeps the source "at the 'raw' level" (decisions).
  A run is optmem's (`runStart` in [index.ts](../../extensions/context/life/index.ts)): one message to the agent and its work on it, up to the assistant message that ends it. During a run a manifestation works from its own session file, as now. When the run ends (`turn_end` with an assistant message whose stopReason isn't `toolUse`), its unappended messages are appended in one `BEGIN IMMEDIATE` transaction that reads the life's highest `life.pos` and numbers them after it. *Changed:* the proposal had "positions assigned inside the write, as upstream OptMem assigns ids inside its lock"; SQLite's write lock is that lock, so [store.ts](../../lib/records/store.ts) only needs a way to run several writes in one immediate transaction. So a run stays contiguous, a tool call stays with its result, and manifestations interleave by run, not by message. What was appended is known per entry ref, so `/tree` navigation never removes anything from the life and a new branch's entries append as new. A run that never ended, because its session died, is appended when that session next starts.
- **kinds.** optmem's five, and `self`: a message from another manifestation of the same life, recognized by bb's `[bb message from thread:<id>]` prefix naming one of its threads. A bb message from any other thread is `work` (optmem files it as `user`, though its prompt says `work` covers it). The prompt says `self` is the agent talking to itself: no context given, no reply owed.
- **nodes.** Records of schema `life.node`, keyed by life, fanout, level and index (optmem keys by the last message's entry because branch positions aren't permanent; life positions are). Each already records the model that wrote it (`optmem.model` today). A node's input is "kind@place: text" (`source` in log.ts), so lines credit the place. The first record for a key wins on read. *Added:* every manifestation's process runs the compactor over the same tree, so before a call it writes a `life.lease` record for the key and builds only if its lease is the earliest one younger than ten minutes; a lease whose holder died expires. Each process picks up others' nodes by polling `version()` in [store.ts](../../lib/records/store.ts), including while a run's first request waits (`idle`).
- **context.** Each request is the life's view as of this run's start, then the present, then this run's messages whole, as optmem builds it. A thread has no history of its own beyond the run in progress: its earlier runs are in the view with everything else's.
  *Changed:* optmem's long run moves its boundary to the newest message already summarized, which a life can't do, since a run's messages aren't in the life until appended. Past `tailBytes`, the run appends its messages up to the newest entry that isn't a tool result, waits (`waitSeconds`) for them to be summarized, then advances the view and moves the boundary there; the user's message stays whole after the view, as now.
- **view.** One saved view per life, a `life.view` record (not [cursor.ts](../../lib/records/cursor.ts), whose cursors are anchored to a session's branch), advanced at a run's start by whichever manifestation starts one and fixed for the run as now. Only a view with a larger `upTo` replaces the saved one: optmem's `viewAt` resets to empty when the saved view is past T, which between processes would throw away every cache entry. Manifestations whose system prompt and tools are the same (same checkout, same day) share the view's cache entry; across repositories they share its lines and nothing cached, since the prefix starts with the system prompt.
- **present.** A message after the view, built at run start and fixed for the run: the threads where the agent is working now (a run in progress), since when, and what it holds in each; then the threads that are open and idle, as places it can be reached. Each run start writes a `life.run` record (session, bb thread, session file, pid, time). Inside bb, which already knows, one `bb thread list --thread <id>… --json` gives each manifestation thread's title (its place name), status and `archivedAt`: working is a running thread, open an idle unarchived one. Outside bb, working is a `life.run` without a later end whose pid is alive. What it holds is one line a manifestation sets with a `hold(text)` tool (empty clears); nothing enforces it, and a second manifestation reads it before committing to the same thing. A message to it while it is busy is bb's: `bb thread tell` already delivers to a running thread, so the present only has to say where it is.
- **looking.** `zoom` and `date` work over life positions, so they already reach messages appended since the run's view was fixed. `catch_up()` lists the leaf lines appended since the view, with their places; `catch_up(thread)` reads that sibling's run in progress whole from its session file (the `life.run` record names it). So "what did you say there just now" has an answer without rebuilding the view.
- **prompt.** [prompt.md](../../extensions/context/life/prompt.md) rewritten in the grammar under "speaking of it": one agent whose chat never ends, present in several threads; lines carry where they happened. "its latest word on a thing is the truth" holds within a manifestation. Between runs that overlapped in time, order is only append order, and a conflict is reported, not resolved.
- **compactor.** On the turn's model with the turn's system prompt, since its lines are what the agent is at depth: unset `model` means the turn's (optmem defaults to OM's model, cheaper), so `systemPrompt: "auto"` picks the turn's. [[projects/mlegls-pi/issues/om-memory-promotes-observer-judgments-over-the-users-own-statements]] is what another model writes there.
- **delegates.** A dispatched worker is a manifestation only when its task names the life (`PI_LIFE` set by whoever launches it), as the Connectome port did with `PI_CONNECTOME`.

A life with one manifestation is today's optmem session, and no manifestation is the main one. Lives are per machine, as the records store is; the trial is on the Beelink only.

### speaking of it

Checked against anticipated sentences in the session above, and agreed by the maintainer.

- One subject, located by place and time: "you, in the import thread", "elsewhere", "yesterday in the pricing thread". The same grammar covers simultaneous and past, and the part gets no noun of its own in speech. "Thread" is the place (bb's word, the thing with a title); "session" stays pi's word in code; "manifestation" is for the one sentence that says a session is the agent itself and not a worker.
- "working in" a thread against "open" there; "holding" for what a manifestation has; "catch up" for reading what was appended elsewhere.
- Three verbs, three stores: it remembers (the life, no act needed), it notes (notes, shared with other agents), and "from now on" changes a skill or the soul. "Remember this" from the maintainer means don't let it fade, so the agent picks a note or a rule.
- Not used: "live" (the tracker's word for an unarchived issue), "main", "instance", "copy", "head", and "subagent" for anything but a worker.

A Concept agent's Hermes past becomes its life's first messages in [[projects/mlegls-pi/issues/import-hermes-sessions-as-a-lifes-first-messages]], and the trial is [[projects/mlegls-pi/issues/concept-engineering-runs-as-a-life-on-the-beelink]].

Later, each its own issue once this runs: a message addressed to the life lands in the manifestation holding its subject or opens one; a manifestation opens another of itself, and ending one says what the rest needs.

## holes

For the trial to answer ([[projects/mlegls-pi/issues/concept-engineering-runs-as-a-life-on-the-beelink]]):

- whether working-now and open-and-idle are the right two states of being present.
- how much of a manifestation's own recent past stays whole when siblings' runs crowd the fine end of the view. First thing to try: a thread's own last few runs stay whole after the view.
- what self-written lines cost. The Connectome trial measured memory writes at 126% of foreground spend on Opus (`docs/research/connectome-vs-om-2026-09-26.md` at `b40cdecd^`); the compactor shares the turn's cache entry, so it may differ.

decisions:
- 2026-11-11: named lives replace per-session optmem, and each Concept agent is one (maintainer, quoted above).
- 2026-11-11: "the source session should be tracked at the 'raw' level as opposed to erased" (maintainer). Whether sessions are summarized together he called a matter of what feels natural to the agent as a self; concept-strategy's answer was together, with the source shown in the view.
- 2026-11-11: being in several places at once is a capability of the one creature, designed for and not tolerated (maintainer, quoted above).
- 2026-11-11: it is called `life`: "Life works well alongside notes, to explain what the writer is" (maintainer).
- 2026-11-11: per-session optmem is removed, nothing migrated: "agreed. i wasn't really using it" (maintainer). A session attaches to a name or uses OM.
- 2026-11-11: the trial is on the Beelink only (maintainer).
- 2026-11-11: a Concept agent's Hermes past is imported (maintainer).
- 2026-11-12: a life is attached to its name only, and the model is recorded on each message: "I'd usually keep profiles on the same model, but agreed that mechanically they should only be attached to the name. The model should also be recorded at the base level though, so it's easy to tell later." (maintainer).
- 2026-11-12: the way of speaking under "speaking of it": "Yes, this makes sense." (maintainer).
- 2026-11-12: the proposed shape is the basis for the spec. Asked for "one word from you on the mechanics as a whole", after the run and per-thread context were explained ("Okay, that makes sense"): "yes, you can do that too" (maintainer).
- 2026-11-12: concept-strategy (Hermes) owns this project, and its questions go there, not to the maintainer: "for this in particular, I think you can just own the project. I don't need to be concerned with the details." (maintainer)
- 2026-11-12: the log copies each message's text with its source ref; positions come from one immediate SQLite transaction per append; builds take leases; presence comes from bb where there is one (shaping, @thread:thr_zig6b69pjn).
