Triage turns a report into understood work or a reason not to do it. The
project's tracker docs define surfaces, role labels, and write authority.
An external PR is a request with attached code when that surface is enabled;
an explicitly named PR is always the review target.

1. Read the report, discussion, prior triage, and code or diff. Search by domain
   concept for existing behavior and prior rejection reasons
   ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
2. Verify the consequential claim: reproduce the symptom or run the contributed
   change where practical. Distinguish a confirmed result from insufficient
   access or detail. `diagnosing-bugs` helps for a hard failure.
3. Present the recommended disposition and proposed comments, briefs, and
   tracker changes for confirmation (`grilling`). A presented batch can be
   approved together; an already-approved exact change needs no new interview.
4. Apply the confirmed disposition within tracker authority. Ready work gets a
   portable [agent brief](AGENT-BRIEF.md); missing information gets the facts
   established so far and specific questions. A rejection gets its reason.

Discovery normally shows untriaged items and `needs-info` items with new
reporter activity, oldest first, with titles and short summaries. Read prior
notes on resumption rather than asking the same questions again. An explicit
state-change request need not repeat the whole triage process.

Canonical category roles are `bug` and `enhancement`; next-state roles are
`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, and `wontfix`.
Keep one current state. Ready-for-human describes the next human action,
including a merge decision, not necessarily human implementation.

Public comments and issues created during triage begin with:

> *This was generated by AI during triage.*

Already implemented and rejected are different dispositions. The former links
to the existing capability; only the latter belongs in rejection memory.
